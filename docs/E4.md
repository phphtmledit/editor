Date: 2026-08-14. Repository: <https://github.com/phphtmledit/editor>.

interface, the light-only visual system, responsive editor layout,

## Theme contract and visual system

The parser continues to read `?theme=`. Missing, `light`, `dark`, `auto`, and
unexpected values all resolve to `data-theme="light"` in MVP. No
`prefers-color-scheme` branch can silently change that result. The outer
document and the TinyMCE iframe both declare `color-scheme: light`, preventing
browser dark-mode form styling or forced inversion from producing a mixed UI.

All project colors are declared once as `--phe-*` root tokens. Production HTML,
TypeScript, and CSS contain no project color literals outside those declarations.
The only accent is `#4F46E5`. TinyMCE vendor files are unmodified; project CSS
maps visible Oxide focus, active, selected, menu, dialog, and status-path states
to the same tokens. The iframe receives the resolved token values explicitly,
so a future theme remains a CSS/token change rather than an editor rewrite.

## English interface and bootstrap safety

All project-owned user-facing strings, including TinyMCE block-format labels,
live in `src/ui/strings.ts`. Vite uses that same typed catalog to replace escaped
static HTML tokens at build time and fails on an unknown or unresolved token.
The runtime hydrator covers dynamic state and accessibility copy. Production
source scans contain no Cyrillic UI text, and TinyMCE uses its built-in English
language with stable ISO date/time formats.

The built HTML contains readable English bootstrap and failure copy before any
module executes. If application JavaScript never starts, a delayed fallback
alert replaces an anonymous blank shell. Initialization and static-copy
hydration share the normal fatal path; a failed editor setup hides unusable
regions and presents the alert instead of leaving an empty workspace.

## Responsive layout and accessibility

At widths of 900 px and above, TinyMCE and CodeMirror use the resizable split
layout. Below 900 px they use keyboard-operable Visual/Code tabs. A breakpoint
transition preserves whichever editor currently owns focus. Pending animation
frames and viewport/listener resources are cancelled during teardown.

`visualViewport` height and offset updates drive the mobile workspace on both
resize and scroll. The final Chromium audit exercised 1440, 1024, and 900 px in
desktop mode plus 899, 768, 390, and 320 px in tab mode. All seven layouts had a
nonzero active editor, no horizontal overflow, correct splitter/tab visibility,
and a working source-panel switch.

The measured color pairs all exceed the 4.5:1 text requirement; the minimum was
`5.197:1`. Focus is visible with the solid accent and is not removed from TinyMCE
dialogs or menus. Under emulated `pointer: coarse` and `hover: none`, all 33
visible baseline controls were at least 44×44 px, including shell actions,
TinyMCE menubar/toolbar controls, and the status-path item that previously
exposed the smallest target. Permanent cascade/selector tests separately cover
TinyMCE dialog controls and text fields; their runtime geometry remains part of
the E6 manual interaction matrix rather than this 33-control claim.

The application contains no E5 About control or link.

## Automated and browser verification

Permanent tests cover theme parsing, light-only TinyMCE configuration and iframe
token transfer, the single English string catalog, production HTML token
replacement, color-literal and contrast contracts, touch selectors, responsive

The final browser scenario used Chrome 151.0.7922.138 and CDP 1.3 with fresh

HTML import, actual DOCX drop into the TinyMCE iframe, download, clipboard,

cleaning run took 185.9 ms, below the 500 ms limit.

## Performance and Network evidence

The final captures are bound to production manifest SHA-256
`6be1fdc43f3b32cca7fb2119c707f78f4e6150531950a237640061d8914d252e`.
`npm run size` recompresses the exact manifest-bound files rather than relying
on HAR wire-size estimates.

| Metric | Measured | Budget | Margin | Verdict |
| --- | ---: | ---: | ---: | --- |
| Cold editor-ready transfer, gzip | 572,129 B | 600,000 B | +27,871 B | PASS |
| Cold editor-ready transfer, Brotli | 486,385 B | 500,000 B | +13,615 B | PASS |
| E4 cumulative transfer, gzip | 716,821 B | 750,000 B | +33,179 B | PASS |
| E4 cumulative transfer, Brotli | 604,281 B | 630,000 B | +25,719 B | PASS |
| Cold-load HTTP requests | 18 | 25 | +7 | PASS |

The cumulative inventory contains 22 requests. It adds exactly the rich-source
entry, safe replacement entry, isolated regex Worker, and optimized Mammoth
entry to the cold set. The custom icon and 300-entry emoji resources are each
requested once; default icons, stock emoji data, dark skins, fixtures, and DOCX
test files are absent. Mammoth is absent cold and loads exactly once for the
actual DOCX drop. Every application request is a successful local GET; there
are no Tiny domains, third-party origins, cache/service-worker responses,
console failures, cookies, authorization headers, response bodies, or document
text in the sanitized evidence.

Compared with accepted E3, the finished E4 interface adds 2,498 B gzip and
1,824 B Brotli to the cold scenario while retaining 13,615 B of cold Brotli
headroom. Initial application JavaScript outside TinyMCE is supplementary
evidence at 135,905 B gzip / 116,588 B Brotli, within its 150,000/130,000
limits.

The regular-expression Worker retains the documented split-session HAR
limitation: Chrome exposes a real response/data/terminal lifecycle and exact
decoded size, but not a reliable compressed header/body split. No synthetic
wire sizes are inserted, and budget calculations remain independent.
