# E5 — embedding, legal links, deployment evidence, and delivery budgets

Date: 2026-08-21. Repository: <https://github.com/phphtmledit/editor>.

This report covers the E5 implementation and automated evidence required by
`docs/TZ.md` version 2.9. It adds the browser-visible source and license links,
the documented iframe contract, Cloudflare Pages response-policy generation,
the final action icons, and the deployed performance and delivery measurements.
The accepted E0–E4 reports and their immutable evidence remain unchanged.

The current E5 candidate is merged and deployed. The verified production build
comes from commit `45ff34b568e7e21f53dbc794a05c606b51bdc93d`; its immutable
Cloudflare URL is `https://97794bf1.phphtmledit-editor.pages.dev/`. The
custom-domain status is **Active**, SSL is enabled, and
`https://app.phphtmledit.com/` serves the same E5 asset entrypoints, including
the About menu and both mobile/bootstrap paint corrections. Live root,
hashed-asset, and `/licenses.txt` headers have been verified.

Host integration remains incomplete for a measured reason. The instrumented
attempt-2 pre-iframe baseline and iframe insertion are complete. The first two
after series exposed and retained mobile-tab and TinyMCE/Oxide layout shifts.
The current busy-editor paint guard removes that iframe-attributable CLS: the
valid attempt-4 result is zero in all five runs. Strict criterion 12 still
fails because FCP, LCP, Speed Index, and TBT regress when the loaded editor
intersects the first viewport. The positive framing and clipboard checks and
the negative `phe-preview.com` framing check are also still pending.

## E5 interface additions

TinyMCE now has one **About** menu containing exactly two commands: **Source
code** and **Third-party notices**. The first targets the public GitHub
repository and the second targets the generated `/licenses.txt` artifact. Both
commands were exercised through real native new-page creation. Each created
exactly one top-level browsing context, both child contexts had a null opener,
and the temporary anchors were removed. The notices response was separately
verified as HTTP 200, `text/plain; charset=utf-8`, without an attachment
disposition. These destinations are top-level navigations, not resources in the

cold and cumulative payload budgets.

soft background token. The former indigo is absent. Native checkboxes,

## Embedding and hosting contract

`docs/EMBEDDING.md` documents the exact lazy iframe, its reserved height,
accessible title, and clipboard delegation. The frame deliberately has no
`sandbox` and no fullscreen permission. The stable `?theme=` parameter remains
light-only in the MVP, and there is no host-to-editor `postMessage` API.

The production build emits Cloudflare Pages `_headers` rules for the
`frame-ancestors` allow-list, no-index policy, immutable hashed assets, and
plain-text license delivery. The build deliberately omits `X-Frame-Options`.
`FRAME_ANCESTORS` must keep `'self'`, `https://phphtmledit.com`,
`https://www.phphtmledit.com`, and `http://localhost:*`; it must never include
`phe-preview.com`.

These generated artifacts and configuration guards are automated. The
Cloudflare custom domain is **Active** with SSL enabled. The current verified
deployment comes from `45ff34b568e7e21f53dbc794a05c606b51bdc93d` at immutable
URL `https://97794bf1.phphtmledit-editor.pages.dev/`. The live root,
hashed-asset, and license headers match the generated policy. The lazy iframe
has been inserted on the public host and the busy-visibility correction has
been remeasured. Exercising the two allowed origins plus the denied origin
remains an external manual step.

## Same-run readiness-mark audit

The previously compared 5,693.5 ms product mark and 7,601.7 ms trusted-input
median came from different diagnostic series. A single replacement run placed
both endpoints in the same navigation. The product
`phe:bootstrap:editor-ready` mark occurred at 5,222.0 ms and trusted TinyMCE
input was accepted at 5,397.5 ms, a 175.5 ms gap. Source focus never occurred,
the rich-source chunk was not requested, the current passive state was rechecked
before arming, and the accepted event was trusted. The suspected roughly
1.5-second product-readiness gap was therefore an artifact of comparing unlike
runs, not a hidden initialization tail.

The first diagnostic attempt is preserved as invalid evidence. Its trusted
input had been accepted, but an under-escaped generated JavaScript expression
made the final readback unparsable before timestamps were persisted. It supplied
no metric. A static parse guard was added before the one authorized replacement
run; the invalid attempt was not silently discarded or averaged. Both this
same-navigation probe and the older encoding matrix target historical deployment
`dc818598`; they remain semantic diagnostics and are not relabelled as timing
evidence for the current build.

## Slow 4G diagnostic

Slow 4G remains a required publication profile at 1.6 Mbit/s down, 750 kbit/s
up, 150 ms latency, and 4× CPU slowdown. It has no absolute time threshold. It
blocks a stage only if trusted-input readiness regresses by more than 15% from
the accepted previous stage.

| Diagnostic median | Accepted E4 reference | E5 | Change |
| --- | ---: | ---: | ---: |
| Navigation → trusted input | 8,529.3 ms | 6,305.6 ms | −2,223.7 ms (−26.071%) |
| Navigation → proven skeleton paint | not comparable | 680.0 ms | not computed |

E5 improves trusted-input readiness, so it does not trigger the regression
block. The accepted E4 paint samples proved that the skeleton covered FCP in
only one of three runs; consequently no three-run E4 skeleton median is
claimed. All three current E5 runs prove that the skeleton is the first
contentful paint. Their readiness values were 5,865.1, 6,305.6, and 7,862.5 ms.
The E5 680 ms skeleton and 6,305.6 ms readiness medians are published
diagnostics, not failures against the desktop-only 1,000/2,500 ms limits.

A fresh comparison attempt is preserved separately as invalid rather than
being used to replace the accepted E4 baseline: its fresh E4 side completed
only 2/3 strict whole-run captures because one run lacked skeleton-at-FCP proof.
No run was repeated or cherry-picked. The attempt embeds the same three valid
current-E5 runs used by the accepted derived comparison.

## Local compression versus delivered bytes

`npm run size` and the deployed delivery budget answer different questions and
must not be substituted for one another:

- the local report takes the manifest-bound canonical local request graph and
  deterministically recompresses the exact files with Brotli quality 11. Its
  488,672 B cold result is a fast relative indicator and an explicit lower
  estimate;
- the historical production encoding report observes a separate deployed graph
  from `dc818598` at a different capture time. Across three runs it saw 18 eager
  responses per run: all 54
  response observations used `Content-Encoding: br` over HTTP/2. The run with
  the median full-wire total recorded 578,716 B of encoded bodies plus 7,326 B
  of headers/protocol overhead, or 586,042 B full wire. The independently
  computed median headers/protocol overhead across the three runs was 7,329 B.

The current blocking desktop median is 586,005 B, which is 97,333 B more than
the local Brotli-11 estimate, about 19.9% of the local value, and leaves 63,995 B
below the delivery ceiling. The historical encoding matrix proves that its
difference was not a gzip fallback: every observed document, script, and
stylesheet response was Brotli encoded. It is intentionally reported as an
earlier deployment diagnostic rather than evidence for the current build.

The delivery timeline is also non-additive because network transfer, parsing,
and initialization overlap. Its median observations were 411.6 ms for document
connection setup, a 4,686.291 ms network window with concurrent parsing and
initialization, and a 446.016 ms post-network initialization tail. The serialized
transfer-demand floor was 2,930.21 ms; it must not be added to those overlapping
wall-clock intervals.

## Instrumented host result and remaining verification

The E5 implementation, fresh canonical Network/size evidence, desktop startup
gate, Slow 4G publication, current deployed-wire budget, production deployment,
live-header verification, pre-iframe baseline, iframe insertion, and matching
post-embed series are complete. Portable raw Lighthouse and probe inputs plus a
semantic manifest are stored under `reports/`; the permanent hosting verifier
recomputes the profile, geometry, load state, medians, and verdict rather than
depending on ignored `work/` files. Integrity mode `npm run hosting:evidence`
passes for this package; criterion-12 mode `npm run hosting` deliberately exits
nonzero. Neither mode claims to execute the remaining manual criterion-7
clipboard checks or criterion-14 framing checks.

The accepted attempt-2 before series had median FCP/LCP 1,931.0523 ms, Speed
Index 2,434.91882 ms, TBT 0 ms, and CLS 0. The reserved slot crossed the first
fold at exactly 531.53125–1,272.21875 CSS px in every 412×823 run; it contained
no iframe and caused no application request.

Attempt 4 used the identical profile, viewport, scroll position, and exact slot
geometry. In all five runs the canonical lazy iframe occupied the slot, fired
its direct load event, and loaded one application Document plus 18 completed
application requests from build
`45ff34b568e7e21f53dbc794a05c606b51bdc93d`. The busy-editor visibility fix
worked: after CLS is exactly 0 in all five raw Lighthouse reports, with no
main-frame or subframe layout-shift item.

Strict criterion 12 nevertheless fails four of five metrics:

| Metric | Before median | After median | Change | Verdict |
| --- | ---: | ---: | ---: | --- |
| FCP | 1,931.0523 ms | 2,743.3753 ms | +812.3230 ms (+42.07%) | FAIL |
| LCP | 1,931.0523 ms | 2,743.3753 ms | +812.3230 ms (+42.07%) | FAIL |
| Speed Index | 2,434.91882 ms | 3,300.734963 ms | +865.816143 ms (+35.56%) | FAIL |
| TBT | 0 ms | 416.0 ms | +416.0 ms | FAIL |
| CLS | 0 | 0 | 0 | PASS |

The reference-only Performance score median changes from 98 to 81. This is a
valid failure, not an instrumentation gap: the iframe intersects the first
viewport and demonstrably loads in every run. Its 18 requests compete with the
host load, and TinyMCE/theme long tasks execute after host FCP. Repeating the
same series, moving the frame below the fold without loading it, or using the
composite score would not satisfy the specification.

The portable LHR/probe package does not contain response bodies, so it cannot
cryptographically prove that host HTML differed only by iframe activation. It
does prove the exact URL/profile/viewport/scroll/slot geometry, the stable host
resource inventory, and the frame/build load state. This is a stated limit on
causal attribution, not a reason to turn the observed regression into a pass.

The following external/manual checks remain open:

1. verify allowed framing and successful clipboard delegation on
   `phphtmledit.com` and `www.phphtmledit.com`;
2. verify the no-`allow="clipboard-write"` fallback without a false success
   message;
3. verify that `phe-preview.com` is denied by CSP;
4. resolve criterion 12 through an explicitly approved product/host-loading
   change or specification decision, then measure that new state without
   overwriting the retained failed result.

Until then, specification 2.9 criteria 7, 12, and 14 remain open.
