## Theme contract and visual system

The parser continues to read `?theme=`. Missing, `light`, `dark`, `auto`, and
unexpected values all resolve to `data-theme="light"` in MVP. No
`prefers-color-scheme` branch can silently change that result. The outer
document and the TinyMCE iframe both declare `color-scheme: light`, preventing
browser dark-mode form styling or forced inversion from producing a mixed UI.

All project colors are declared once as `--phe-*` root tokens. Production HTML,
TypeScript, and CSS contain no project color literals outside those declarations.
The only accent is `#4F46E5`. TinyMCE vendor files are unmodified; project CSS
maps visible Oxide focus, active, selected, menu, dialog, and status-path states
to the same tokens. The iframe receives the resolved token values explicitly,
so a future theme remains a CSS/token change rather than an editor rewrite.

## English interface and bootstrap safety

All project-owned user-facing strings, including TinyMCE block-format labels,
live in `src/ui/strings.ts`. Vite uses that same typed catalog to replace escaped
static HTML tokens at build time and fails on an unknown or unresolved token.
The runtime hydrator covers dynamic state and accessibility copy. Production
source scans contain no Cyrillic UI text, and TinyMCE uses its built-in English
language with stable ISO date/time formats.

The built HTML contains readable English bootstrap and failure copy before any
module executes. If application JavaScript never starts, a delayed fallback
alert replaces an anonymous blank shell. Initialization and static-copy
hydration share the normal fatal path; a failed editor setup hides unusable
regions and presents the alert instead of leaving an empty workspace.

The TinyMCE core is no longer an executable parser-blocking script in the
initial HTML. The document contains one exact
`<link rel="preload" as="script">` for
`/tinymce/tinymce.min.js?v=8.8.2`, preserving the early download without
executing the runtime during HTML parsing. After the loading skeleton reaches
the browser's first contentful paint, the bootstrap waits for the following
task, inserts one asynchronous script with that same URL, waits for both its
`load` event and a valid `globalThis.tinymce`, and only then calls
`tinymce.init`. Concurrent loader calls share one promise, an already valid
runtime is reused, and failed or incomplete loads follow the same readable
fatal path. A terminal `pagehide` cancels every pending boundary and prevents a
late editor from appearing on a discarded page.

## Responsive layout and accessibility

At widths of 900 px and above, TinyMCE and CodeMirror use the resizable split
layout. Below 900 px they use keyboard-operable Visual/Code tabs. A breakpoint
transition preserves whichever editor currently owns focus. Pending animation
frames and viewport/listener resources are cancelled during teardown.

`visualViewport` height and offset updates drive the mobile workspace on both
resize and scroll. The final Chromium audit exercised 1440, 1024, and 900 px in
desktop mode plus 899, 768, 390, and 320 px in tab mode. All seven layouts had a
nonzero active editor, no horizontal overflow, correct splitter/tab visibility,
and a working source-panel switch.

The measured color pairs all exceed the 4.5:1 text requirement; the minimum was
`5.197:1`. Focus is visible with the solid accent and is not removed from TinyMCE
dialogs or menus. Under emulated `pointer: coarse` and `hover: none`, all 33
visible baseline controls were at least 44×44 px, including shell actions,
TinyMCE menubar/toolbar controls, and the status-path item that previously
exposed the smallest target. Permanent cascade/selector tests separately cover
TinyMCE dialog controls and text fields; their runtime geometry remains part of
the E6 manual interaction matrix rather than this 33-control claim.

The application contains no E5 About control or link.

## Loading, DOCX progress, and errors

The accepted E4 build still loaded TinyMCE as a classic script in `head`; that
held the parser until the core arrived. A first attempted repair using
`requestAnimationFrame` followed by a task was rejected by the strict preflight:
the dynamic script was inserted at 2,993 ms and loaded at 3,017 ms, while FP/FCP
did not occur until 3,028 ms. That failed run wrote no canonical reports.

The final bootstrap waits specifically for a buffered
`first-contentful-paint` entry and then crosses a task boundary. Where Paint
Timing is unavailable, the best-effort fallback is two animation frames and a
task, with no arbitrary watchdog capable of racing the paint. The canonical
capture uses a document-start state sampler and buffered
`PerformancePaintTiming`; all five product marks are retained in exact order:
paint handoff, script insertion, TinyMCE runtime loaded, initialization started,
and editor ready.

| Measurement | Navigation → first skeleton paint | Skeleton paint → editor ready | Navigation → editor ready |
| --- | ---: | ---: | ---: |
| Accepted E4 before loader repair | 476.0 ms | 44.6 ms | 520.6 ms |
| Final canonical cold capture | 1,368.0 ms | 387.0 ms | 1,755.0 ms |
| Final canonical cumulative capture | 160.0 ms | 349.2 ms | 509.2 ms |
| Separate throttled 4G diagnostic | 468.0 ms | 3,284.9 ms | 3,752.9 ms |

These are observed latency diagnostics from separate fresh profiles, not byte
budgets or a claim of faster total startup. The invariant is ordering: the
first contentful paint contains the nonzero busy skeleton, the executable Tiny
script is inserted afterwards, and the skeleton remains until the fixed
`phe:bootstrap:editor-ready` mark. In the throttled profile (1.6 Mbps down,
750 Kbps up, 150 ms latency, no CPU throttling), the preload began at 191.0 ms,
FCP was 468.0 ms, executable insertion was 1,829.2 ms, the runtime loaded at
2,011.2 ms, and editor ready was 3,752.9 ms. The Tiny core had one network
request and was reused from the preload.

DOCX import showed its busy state before parsing and restored controls after
completion. Progress/status text is not dimmed by ancestor opacity, so its
effective contrast remains valid. Expected failures and stale asynchronous
results retain the explicit English messages introduced in earlier stages.

## Automated and browser verification

Permanent tests cover theme parsing, light-only TinyMCE configuration and iframe
token transfer, the single English string catalog, production HTML token
replacement, color-literal and contrast contracts, touch selectors, responsive
focus/layout behavior, `visualViewport`, lifecycle cleanup, bootstrap/fatal
states, and the existing E0–E3 behavior.

The final browser scenario used Chrome 151.0.7922.138 and CDP 1.3 with fresh
profiles, cache disabled, and service workers bypassed. In addition to all E4
theme/layout/accessibility/state checks, it replayed the complete E3 inventory:
source rich tools, cleaning and isolated regex timeout, emoji search/insertion,
HTML import, actual DOCX drop into the TinyMCE iframe, download, clipboard,
sample, draft, and new-document actions. The 100,000-character cooperative
cleaning run took 204.6 ms, below the 500 ms limit.
