# E2 — cleaning, replacement and mass-operation undo

Date: 2026-08-14. Repository: <https://github.com/phphtmledit/editor>.

This report closes the E2 scope from `docs/TZ.md` §9: ten cleaning rules,
format/minify actions, ordered find-and-replace rules with regular expressions,
one shared mass-operation undo stack, and automated tests for the cleaning
product core. It deliberately does not start E3 import/export, E4 final
themes/UI, or E5 embedding and interface links.

The accepted E0 gate remains closed. Its immutable evidence stays in
`docs/E0.md` and `reports/network-{cold,full}.har`; E1 remains preserved in
`docs/E1.md` and the `network-e1-*`/`size-e1-result.json` files. E2 did not
rewrite those baselines.

## Cleaning product core

The document-tools section exposes all ten specified rules individually and as
one configurable run. The eight documented defaults are enabled; “tag
attributes” and “plain text” remain opt-in. The prominent “AI symbols” row
normalizes smart quotes, en/em dashes, zero-width characters and narrow spaces.
Settings use a bounded, versioned `localStorage` record and recover to defaults
with a visible warning when storage is unavailable or invalid.

Rules operate through DOM APIs on one detached document, never by applying a
regular expression to the HTML string. Their canonical execution order removes
Word metadata before generic classes/styles, then performs textual and empty
structure cleanup. The complete selected-rule run yields to the browser event
loop between rule passes while retaining the same detached DOM. This lets input,
painting and timers proceed without paying for repeated parse/serialize cycles;
each individual DOM rule remains atomic.

The Word rule handles conditional comments, Office namespaces, Word desktop and
Word-for-web classes/attributes, EOP/separator spans and empty Office wrappers.
Before presentation styles are removed, meaningful Word TextRun formatting is
promoted to semantic `strong`, `em` and `u` elements. Lists, paragraphs, links
and ordinary non-Office attributes survive the Word-specific pass. Repeated
spaces collapse through adjacent inline wrappers but stop at block, void and
preformatted boundaries; an isolated semantic NBSP such as `10&nbsp;kg` is
preserved.

The committed clipboard fixture was captured from a real Microsoft Word for
the web paste operation, not generated from DOCX:

  `b29b485dba7d5ac3fd5cf1ad455283e59c5b7145544d2529f57ee4699a25a50c`;

The fixture contains no URL, email address or personal data. Exact-output,
metadata-removal, semantic-formatting, privacy and idempotence assertions are
permanent tests. The production boundary gate hashes every file under
`tests/fixtures` and rejects any occurrence in `dist`; the Word fixture is not
part of the browser bundle or any request inventory.

“Format” and “Minify” are separate mass actions. Formatting produces stable
indentation and line breaks; minification removes unnecessary inter-tag and
line-break whitespace without rewriting text content. Both are idempotent in
the tested domain.

## Replacement and safety

The replacement panel supports up to ten ordered rules with literal/regular
expression and case-insensitive modes. Rules are stored in a bounded, versioned
schema. Literal replacement keeps `$` replacement tokens literal; regular
expressions use native capture replacement semantics. Invalid, empty or
oversized rules are reported as data and marked with accessible error state
instead of throwing. Individual and batch results show exact replacement
counts, and a bad batch entry does not prevent later entries from running.

A valid regular expression never executes on the UI thread. The safe module is
loaded only for a regex action and creates a disposable module Worker with a
hard 500 ms limit per rule. A pathological `(a+)+$` case is terminated, returns
`regex-timeout`, leaves the document byte-for-byte unchanged and keeps the UI
responsive. The internal error code is asserted by Vitest; the production UI
exposes the useful localized message and `aria-invalid`, not an implementation
code.

Every asynchronous cleaner or regex result is tied to its exact input snapshot.
Immediately before a mass write, the active editor is flushed again and the
current source is compared with that snapshot. If the user edited either panel
while the operation was pending, the stale result is discarded with a visible
message. Tests reproduce this race for both cooperative cleaning and the regex
Worker.

## Mass writes and undo

E2 does not reuse the E1 synchronization writer. Normal focus-authority
synchronization continues to preserve both native histories, selections and
scroll positions. A cleaning, format, minify or replacement action instead
uses a distinct guarded path that writes both editors and resets TinyMCE and
CodeMirror histories.

Before crossing that reset boundary, the application stores the authoritative
HTML and operation label. One memory-only stack is shared chronologically by
cleaning and replacement, holds at most ten snapshots and evicts the oldest
entries above 20 MiB. The single visible Undo button describes the next action;
there is no second replacement-specific undo and no keyboard shortcut for this
stack. Undo restores both panels through the same mass path and resets their
native histories again. A snapshot remains recoverable even if TinyMCE
normalizes the proposed result back to the original serialization or a writer
throws.

Browser integration confirmed that native `Ctrl/Cmd+Z` cannot cross a mass
boundary, while the application button restores both panels to identical HTML.
TinyMCE `xss_sanitization: true` remains enabled; E2 configures allowed content
instead of disabling the sanitizer.

## Tests and performance

Vitest and jsdom are exact dev-only dependencies. They do not enter the product
graph and remain outside the runtime-license gate defined by `docs/TZ.md` §3.1.
The suite contains 67 passing tests across 20 files. It includes input→expected
output coverage for every cleaning rule, real Word clipboard HTML,
typographic/AI artifacts, combined formatting, inline-boundary whitespace,
format/minify idempotence, storage failures, regex errors/timeouts, mass stack
bounds, native CodeMirror history reset and stale asynchronous operations.

The final Chrome 151 cumulative scenario cleaned a 100,000-character document
with the default eight-rule cooperative run in **187.6 ms**, measured from the
action to `aria-busy=false` with a MutationObserver. This is below the 500 ms
budget by 312.4 ms and includes the inter-rule event-loop yields. A separate
jsdom diagnostic measured the unchanged synchronous core at 357.7 ms cold and
206.3–249.6 ms warm; it is supporting evidence, not the browser acceptance
number.

used by DevTools Network, with cache disabled and service workers bypassed.
Cold and cumulative scenarios use separate temporary profiles. The cumulative
run exercises all ten individual rule buttons, the 100,000-character selected
run, format, minify, literal replacement, pathological regex timeout, batch,
remove and common undo.

The cold Brotli margin is only 1,479 B, so future eager code or dependencies
must be measured rather than assumed harmless. Initial application JavaScript
outside TinyMCE is supplementary evidence at 129,135 B gzip / 111,194 B
brotli, still below 150,000/130,000.

The 18-request cold inventory contains the application, eager CodeMirror HTML
highlighting and self-hosted TinyMCE only. The 21-request cumulative inventory
adds exactly `source-rich`, `safe` and `regex-worker`, each once. Stock TinyMCE
icons, Mammoth, DOCX/HTML fixtures, Tiny Cloud domains, caches and service
workers are absent. All application requests are local successful GETs, and the
sanitized HARs contain no bodies, cookies, authorization headers or document
text. The captures are bound to manifest SHA-256
`92f015457d9cfd2aba016a7f28ea39e4f9924209ab7007f0aab679139e92f358`.

The Worker request crosses page and Worker CDP sessions. Its lifecycle contains
one request, response/data events and a real `Network.loadingFinished`; decoded
size equals the 1,655-byte current file and no duplicate is synthesized. Chrome
does not expose a byte-accurate gzip body split for this request, so its HAR
`headersSize`/`bodySize` are honestly `-1`, `compression` is omitted and the
observed encoded length is retained as an implementation detail. The four
budgets never use HAR wire sizes: `npm run size` recompresses each exact current
`dist` file deterministically with gzip-9 and Brotli-11 and rejects a stale
manifest fingerprint.

## E3 size prerequisite

E3 must begin by reducing the Mammoth runtime chunk before adding import/export
orchestration. The current diagnostic Mammoth chunk is 123,960 B gzip / 102,259
B Brotli. Adding it unchanged to E2 cumulative weight projects **765,056 B gzip
and 646,000 B Brotli**, already 15,056 / 16,000 B above the
750,000/630,000 ceilings before the first line of E3 product code.

The accepted diagnosis remains: remove dead Bluebird and xmlbuilder paths and
avoid importing all of Underscore. `dingbat-to-unicode` stays because real Word
documents need its Wingdings/Symbol conversion. E2 does not start that work.
