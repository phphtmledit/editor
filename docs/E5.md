# E5 — embedding, legal links, deployment evidence, and delivery budgets

Date: 2026-08-21. Repository: <https://github.com/phphtmledit/editor>.

This report covers the E5 implementation and automated evidence required by
`docs/TZ.md` version 2.9. It adds the browser-visible source and license links,
the documented iframe contract, Cloudflare Pages response-policy generation,
the final action icons, and the deployed performance and delivery measurements.
The accepted E0–E4 reports and their immutable evidence remain unchanged.

The E5 candidate is merged and deployed. The first verified E5 production
application deployment was built from commit
`b3dc011b5f3381e10237f6af6c2c7f7a55d9e955`; its immutable Cloudflare URL is
`https://0e13e6fa.phphtmledit-editor.pages.dev/`. The custom-domain status is
**Active**, SSL is enabled, and `https://app.phphtmledit.com/` visibly serves E5,
including the About menu. Live root, hashed-asset, and `/licenses.txt` headers
have been verified.

Host integration remains incomplete. A new instrumented pre-iframe baseline,
iframe insertion, the matching five-run post-embed Lighthouse comparison, the
positive framing and clipboard checks, and the negative `phe-preview.com`
framing check are still pending.

## E5 interface additions

TinyMCE now has one **About** menu containing exactly two commands: **Source
code** and **Third-party notices**. The first targets the public GitHub
repository and the second targets the generated `/licenses.txt` artifact. Both
commands were exercised through real native new-page creation. Each created
exactly one top-level browsing context, both child contexts had a null opener,
and the temporary anchors were removed. The notices response was separately
verified as HTTP 200, `text/plain; charset=utf-8`, without an attachment
disposition. These destinations are top-level navigations, not resources in the
editor document graph, so their bytes are intentionally outside the editor
cold and cumulative payload budgets.

The six shell actions now use project-authored, accessible icons for opening a
file, downloading HTML, copying HTML, copying text, loading the sample, and
creating a new document. Their labels remain visible; the icons add visual
scanning cues without replacing the text. The rolling 68-icon audit verifies
the six new contracts together with TinyMCE toolbar, menu, dialog, and fallback
coverage.

The final light palette uses `#0B6BCB` as the only accent and `#E6F1FB` as the
soft background token. The former indigo is absent. Native checkboxes,
radios, and ranges inherit `accent-color: var(--phe-accent)`. Computed Oxide
focus, primary-button, checkbox, active-menu, and dialog states resolve to the
same token system. Soft-blue states retain normal text color rather than using
the low-contrast soft token as text. The measured minimum contrast is
`4.914:1` for muted text on the soft background, above the `4.5:1` threshold.

## Embedding and hosting contract

`docs/EMBEDDING.md` documents the exact lazy iframe, its reserved height,
accessible title, and clipboard delegation. The frame deliberately has no
`sandbox` and no fullscreen permission. The stable `?theme=` parameter remains
light-only in the MVP, and there is no host-to-editor `postMessage` API.

The production build emits Cloudflare Pages `_headers` rules for the
`frame-ancestors` allow-list, no-index policy, immutable hashed assets, and
plain-text license delivery. The build deliberately omits `X-Frame-Options`.
`FRAME_ANCESTORS` must keep `'self'`, `https://phphtmledit.com`,
`https://www.phphtmledit.com`, and `http://localhost:*`; it must never include
`phe-preview.com`.

These generated artifacts and configuration guards are automated. The
Cloudflare custom domain is **Active** with SSL enabled and serves the deployed
E5 candidate from production `main`. The live root, hashed-asset, and license
headers match the generated policy. Inserting the lazy iframe on the public
host and exercising the two allowed origins plus the denied origin remain
external manual steps.

## Blocking desktop startup gate

The inherited startup gate uses a dedicated CDP harness configured to the exact
Lighthouse desktop transport profile: 10,240 kbit/s, 40 ms latency, and no CPU
throttling. These three startup measurements are not Lighthouse CLI audits.
Each fresh deployed run used a cache-disabled profile and trusted TinyMCE input
acceptance as the readiness boundary. The skeleton was nonzero at FCP in every
run.

| Three-run median | Measured | Limit | Verdict |
| --- | ---: | ---: | --- |
| Navigation → skeleton paint | 928.0 ms | 1,000 ms | PASS |
| Navigation → trusted editor-ready input | 1,600.9 ms | 2,500 ms | PASS |
| Deployed full wire | 586,054 B | 650,000 B | PASS |

The dedicated production-delivery diagnostic, captured separately, reports a
586,042 B full-wire median. The 12-byte difference is ordinary run-level
variation; both measurements pass the same 650,000 B ceiling.

## Same-run readiness-mark audit

The previously compared 5,693.5 ms product mark and 7,601.7 ms trusted-input
median came from different diagnostic series. A single replacement run placed
both endpoints in the same navigation. The product
`phe:bootstrap:editor-ready` mark occurred at 5,222.0 ms and trusted TinyMCE
input was accepted at 5,397.5 ms, a 175.5 ms gap. Source focus never occurred,
the rich-source chunk was not requested, the current passive state was rechecked
before arming, and the accepted event was trusted. The suspected roughly
1.5-second product-readiness gap was therefore an artifact of comparing unlike
runs, not a hidden initialization tail.

The first diagnostic attempt is preserved as invalid evidence. Its trusted
input had been accepted, but an under-escaped generated JavaScript expression
made the final readback unparsable before timestamps were persisted. It supplied
no metric. A static parse guard was added before the one authorized replacement
run; the invalid attempt was not silently discarded or averaged.

## Slow 4G diagnostic

Slow 4G remains a required publication profile at 1.6 Mbit/s down, 750 kbit/s
up, 150 ms latency, and 4× CPU slowdown. It has no absolute time threshold. It
blocks a stage only if trusted-input readiness regresses by more than 15% from
the accepted previous stage.

| Diagnostic median | Accepted E4 reference | E5 | Change |
| --- | ---: | ---: | ---: |
| Navigation → trusted input | 8,529.3 ms | 7,601.7 ms | −927.6 ms (−10.875%) |
| Navigation → proven skeleton paint | not comparable | 1,920.0 ms | not computed |

E5 improves trusted-input readiness, so it does not trigger the regression
block. The E4 paint samples proved that the skeleton covered FCP in only one of
three runs; consequently no three-run E4 skeleton median is claimed. All three
E5 runs prove that the skeleton is the first contentful paint. The E5 1,920 ms
skeleton and 7,601.7 ms readiness values are published diagnostics, not failures
against the desktop-only 1,000/2,500 ms limits.

## Local compression versus delivered bytes

`npm run size` and the deployed delivery budget answer different questions and
must not be substituted for one another:

- the local report takes the manifest-bound canonical local request graph and
  deterministically recompresses the exact files with Brotli quality 11. Its
  488,667 B cold result is a fast relative indicator and an explicit lower
  estimate;
- the production report observes a separate deployed graph at a different
  capture time. Across three runs it saw 18 eager responses per run: all 54
  response observations used `Content-Encoding: br` over HTTP/2. Its median was
  578,716 B of encoded bodies plus 7,326 B of headers/protocol overhead, or
  586,042 B full wire.

The deployed user receives 97,375 B more than the local Brotli-11 estimate,
about 19.9% of the local value. The difference is not a gzip fallback: every
observed document, script, and stylesheet response was Brotli encoded. The
586,042 B full-wire result remains 63,958 B, or 9.84%, below the 650,000 B
delivery ceiling.

The delivery timeline is also non-additive because network transfer, parsing,
and initialization overlap. Its median observations were 411.6 ms for document
connection setup, a 4,686.291 ms network window with concurrent parsing and
initialization, and a 446.016 ms post-network initialization tail. The serialized
transfer-demand floor was 2,930.21 ms; it must not be added to those overlapping
wall-clock intervals.

## Original host-page Lighthouse baseline

The original host baseline was captured before iframe insertion. Five
Lighthouse navigation runs used one fixed mobile simulated profile. Each run
contained zero iframes, zero references to `app.phphtmledit.com`, and zero
application-domain requests. Its immutable five-run medians are:

| Metric | Median |
| --- | ---: |
| FCP | 1,753.5425 ms |
| LCP | 1,753.5425 ms |
| Speed Index | 1,988.316824 ms |
| TBT | 0 ms |
| CLS | 0.0000592733 |
| Performance score, reference only | 99 |

The score is not an acceptance gate. The five individual runs include scores
of 90 and 99, demonstrating why the independent timing and stability medians
replace the former two-point composite-score allowance.

This series predates specification 2.9 and does not record the reserved editor
slot's position relative to the first viewport or an explicit per-run frame-load
state. It remains historical evidence but cannot be paired with the new
post-embed series for criterion 12. Before inserting the iframe, capture a new
instrumented five-run baseline that records those fields. The matching
post-embed series must use the identical profile, viewport, scroll position,
and slot geometry. Store both new series separately and do not overwrite this
original baseline.
