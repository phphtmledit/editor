# E0 — preparation and risk validation

Date: 2026-08-13. Repository: <https://github.com/phphtmledit/editor>.

This is the report required by `AGENTS.md` before product stage E1. The code in
this repository is an E0-only diagnostic surface: it self-hosts the selected
TinyMCE build, verifies GPL mode, captures the local request set, and runs the
supplied DOCX through Mammoth. It does not implement the two-panel product,
cleaning, source editing, synchronization, persistence, or export.

## Reproducible environment

- Node.js 24.19.0 and npm 11.17.0 (Node satisfies the Vite engine range)
- `tinymce@8.8.2`, `mammoth@1.12.1`
- build-only `vite@8.2.1`, `typescript@7.0.2`
- production preview at `http://127.0.0.1:4173/`
- all package versions are exact; `package-lock.json` is present and will be
  part of the corresponding-source publication
- TypeScript is run only as `tsc --noEmit -p tsconfig.json`; `noEmit: true` and
  `importHelpers: false` are enforced in `tsconfig.json`

## Performance and request budgets

The deterministic size inventory includes the HTML navigation and resources
exposed through `PerformanceResourceTiming` by the top page and the same-origin
TinyMCE iframe. Each current `dist` response is compressed independently with
gzip level 9 and Brotli quality 11. The result, including URL, status and
SHA-256 for every response, is in `reports/size-result.json`. The independent
sanitized HAR 1.2 captures in `reports/network-cold.har` and
`reports/network-full.har` were taken from the Chrome DevTools Protocol Network
domain used by the DevTools Network panel, with cache disabled and service
workers bypassed. Their assertions are in `reports/network-har-result.json`.

| Metric | Measured | Budget | Margin | Verdict |
| --- | ---: | ---: | ---: | --- |
| Cold editor-ready transfer, gzip | 457,531 B | 600,000 B | +142,469 B | PASS |
| Cold editor-ready transfer, brotli | 387,980 B | 500,000 B | +112,020 B | PASS |
| Full cumulative transfer, gzip | 581,488 B | 750,000 B | +168,512 B | PASS |
| Full cumulative transfer, brotli | 490,303 B | 630,000 B | +139,697 B | PASS |
| Cold-load HTTP requests | 18 | 25 | +7 | PASS |

Initial application JavaScript outside TinyMCE is retained as supplementary,
non-budget detail: 3,461 B gzip and 3,046 B brotli. It is not substituted for
either of the two transfer scenarios above.

The self-hosted TinyMCE allow-list also includes the dark skin required by the
later light/dark/auto product UI. The active E0 scenario uses the light skin;
the dark alternative is copied and hash-verified but is mutually exclusive in
a page load and therefore is not added to the light cold-transfer result.

Production `dist` and diagnostic `dist-e0` are separate builds. Production
contains lazy Mammoth but contains no `.docx`, golden HTML, fixture hash, or
fixture-path reference; `npm run e0:build-boundary` enforces this. The diagnostic
build contains both supplied fixtures exactly once under their source hashes.

The stock 112,177-byte `icons/default/icons.min.js` is not distributed or
requested. A deterministic 68-icon pack is generated from TinyMCE 8.8.2 through
the public `IconManager` API and carries a dated modification notice; its exact
current sizes are recorded in `reports/size-result.json`. The emoji database
remains unchanged. The active-light TinyMCE static allow-list footprint (which
also includes `license.md` and `notices.txt`) is recorded separately there.
Cold editor-ready transfer is 457,531 B gzip and 387,980 B brotli.

The full production scenario opened link, image, table, character-map, emoji,
date/time and color UI, then loaded lazy Mammoth without requesting a fixture.
Visual checks covered the toolbar and overflow; File/Edit/View/Insert/Format/Table
menus; link context actions; color palette and picker; image lock states; table
properties and nested Row/Column/Cell menus; and every configured plugin dialog.
Every rendered TinyMCE icon contained an SVG. The `temporary-placeholder` icon
is deliberately absent from the pack, so any omitted required icon becomes the
detectable `!not found!` marker; none appeared across 27 checked UI states, and
the browser log remained empty. The machine-checked evidence is in
`reports/icon-visual-result.json`.

No Tiny Cloud or TinyMCE-domain request was observed in either Network capture.
All 18 cold application requests and all 19 interaction-scenario requests used
the local preview origin. Chrome additionally probed `/favicon.ico` once during
the cold run; that browser-generated 404 is retained in the HAR and excluded
from the application-request budget. All requests were GET, none came from disk
cache or a service worker, and there were no application request failures. The
editor reported TinyMCE 8.8.2, all seven selected plugins, no `fullscreen`
plugin, an editable document, and zero console warnings/errors.
`license_key: 'gpl'` was accepted without a notification or read-only fallback.
The stock default icon pack and diagnostic fixtures were absent; the custom
icon pack was requested once, and the Mammoth chunk appeared only in the full
scenario.

The ≤2.5 s desktop/4G readiness target is not claimed by this local unthrottled
capture. It remains a deployment acceptance measurement; the transfer budgets
above are the E0 evidence available before hosting.

## DOCX smoke test

`tests/fixtures/mammoth-fixture.docx` is 10,360 B with SHA-256
`c96400f26ebef8f76b7a859909583f8ea3f9d6760a60512a54b7d800eaf8bfcc`.
Mammoth 1.12.1 produced zero messages and matched the supplied golden HTML
exactly after whitespace-between-tags normalization.

The structural oracle passed: `h1=1`, `h2=3`, `h3=2`, nested `ol=2` and `ul=2`
with 10 list items, `table=1`, `thead=1`, `tbody=1`, `tr=5`, `th=4`, `td=14`,
plus the expected hyperlink, five `strong` and two `em` elements. The supplied
header row and horizontal merged cell survived.

Known losses are explicit rather than treated as parser failures: direct
underline and Courier New are flattened; list marker/glyph presentation, table
styling, heading colors/sizes, borders and indents are discarded. The fixture
does not cover vertical merge, media, tracked changes, real comments/notes,
macros/OLE, hostile URLs, or the separate clipboard path captured from desktop
Word. The latter remains required for the E2 Word-paste acceptance case.

The lazy Mammoth chunk is 123,957 B gzip and 102,323 B brotli in the current
production build. Its CommonJS graph contains known reducible weight in
Bluebird, xmlbuilder and the full Underscore build, but the fork is deliberately
deferred while the cumulative budget has substantial margin. The
`dingbat-to-unicode` path remains: removing it would regress common Word
documents that use Wingdings or Symbol fonts.

## Licensing and source compliance

- Project manifest and `LICENSE` use `GPL-2.0-or-later`.
- The runtime graph contains 27 unique packages; no Apache-only, proprietary,
  NC, SSPL or BUSL runtime license was found.
- `check-licenses.mjs` starts only from `dependencies`; build-only TypeScript,
  Vite and their trees are outside this gate.
- Nineteen selected TinyMCE vendor assets are copied byte-for-byte and verified
  with SHA-256. The separate project-generated 68-icon pack is a deterministic
  subset of the TinyMCE registry. Баннер набора иконок содержит копирайт и
  лицензионное уведомление TinyMCE, а также датированное уведомление
  проекта об изменении.
- JSZip uses its MIT alternative. `pako` carries both MIT and Zlib terms.
- The legacy `duck@0.1.12` metadata `BSD` is normalized only after exact
  BSD-2-Clause LICENSE hash verification.
- `dingbat-to-unicode@1.0.1` declares BSD-2-Clause but its npm artifact has no
  LICENSE or dated copyright notice. This upstream packaging gap is recorded,
  without inventing a notice; it is not a license incompatibility.
- TinyMCE 8.8.2 vendor metadata is inconsistent: `notices.txt` names DOMPurify
  3.3.2, the outer core banner names 3.4.11, while the executable copies and
  preserved internal banners identify 3.4.12. The distributed code is recorded
  as DOMPurify 3.4.12 under the selected **MPL-2.0** branch. Original TinyMCE
  files remain unchanged.
- Exact upstream permission/disclaimer texts are preserved under
  `third-party-licenses/`; details are in `THIRD-PARTY-NOTICES.md`.
- Every generated application bundle points to the single canonical
  `/licenses.txt` artifact. The legal gate received it over HTTP as
  `text/plain`, with no attachment disposition. A real Chrome link transition
  then rendered the license document in-browser; the temporary test link is not
  part of either production or diagnostic output. The two final product links
  remain scheduled for E5 rather than being added to the E0 surface.
